# TDD Rules

⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라**

## 적용 기준 구분

### 반드시 TDD를 적용하는 대상
- **비즈니스 로직**: 조건부 처리, 상태 변환, 검증, 계산 로직
- **API/라우트**: 요청 처리, 응답 포맷, 에러 케이스
- **유틸 함수**: 재사용되는 헬퍼, 변환/파싱 함수
- **버그 수정**: 재현 테스트 → 수정 → 검증 순서 필수

### TDD가 불필요한 대상
- **타입 정의**: 타입만으로 안전성 확보 (interface, type alias)
- **설정 파일**: .env, config 병합, 상수 정의
- **순수 UI 컴포넌트**: 렌더링만 하는 presentational 컴포넌트
- **SQL/쿼리**: 쿼리 빌더로 생성되거나 ORM에서 제공하는 부분

## RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성
1. **하나의 동작 = 하나의 테스트** → 한 번에 하나만
2. **반드시 실행해서 실패 확인** → 녹색에서 시작하면 규칙 위반
3. **실패 이유가 "기능 미구현"이어야 함**
   - 문법 에러나 타입 오류는 RED가 아님 → 먼저 수정

### GREEN: 최소한의 코드만 작성
1. **가장 짧은 경로로 테스트 통과** (하드코딩 포함 가능)
2. **YAGNI 원칙**: 지금 필요하지 않은 코드는 쓰지 마라
3. **신규 + 기존 테스트 모두 통과 확인** → 회귀 방지

### REFACTOR: 중복 제거 및 개선 (GREEN 유지)
1. **구체적 작업**:
   - 코드 중복 제거
   - 변수/함수명 개선
   - 헬퍼 함수 추출
   - 불필요한 조건 단순화
2. **금지 사항**: 새로운 동작 추가, 기존 테스트 수정
3. **매 단계마다 테스트 실행** → 빨강색 되면 즉시 롤백

### 반복
- 다음 동작에 대한 **RED로 돌아가기**
- 모든 기능이 커버될 때까지 반복

## 삭제 강제 규칙

**테스트 전에 프로덕션 코드를 작성했다면:**
1. 그 코드를 **완전히 삭제** (주석으로 남기지 말 것)
2. **RED부터 재시작**
3. "참고용으로만 남기겠다" → 금지

→ 이렇게 해야 RED-GREEN 사이클의 신뢰성이 유지됨

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 로직이 제일 많은 버그의 원인. 테스트 3줄이면 끝. |
| "나중에 테스트 추가하겠다" | 나중은 없다. 추후 추가 테스트는 98% 작성되지 않음. |
| "시간이 없다" | TDD가 더 빠름. 나중에 디버깅/리팩토링 시간이 훨씬 크다. |
| "삭제하면 이미 작성한 코드가 낭비" | 낭비가 아니라 학습. 테스트 없이 작성한 코드는 빚. |
| "프로토타입이다" | 프로토타입도 TDD. 프로토→ 프로덕션 전환 시 테스트 없으면 위험. |

## 프로젝트별 규칙 우선 조항

**이 파일은 기본값(fallback)입니다.**

프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 명시되어 있으면:
- **그 규칙을 우선 적용**
- 충돌 시 프로젝트 규칙이 이 기본 규칙을 재정의

---

## 도움말

- 테스트 작성 난감? → 하나의 input, 하나의 assert로 시작
- GREEN에 너무 오래? → 정말 최소 코드인지 검증
- REFACTOR에서 테스트 깨짐? → 롤백 후 더 작은 단위로 진행
